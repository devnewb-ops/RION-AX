Estimate Summary

Scope is limited to two items on customrecord_rax_lot: (1) removing the requirement for a user-entered Name value, and (2) ensuring the Item field is automatically set from the Purchase Order line the Lot record is created against. The Name requirement is resolved through native record-type configuration (auto-generated numbering is already enabled), not custom code. The Item autofill requires a new script on the Lot record, since no such logic exists today — the current rax_ue_lot_capture.js User Event only runs on Assembly Build, Item Fulfillment, and Item Receipt, and does not cover Lot records created inline from a Purchase Order line.

Sizing reflects a single-field lookup/set operation with a forced-overwrite rule and one confirmed edge case, standard for a Small User Event script. A key estimate driver and open risk (see Risks) is whether NetSuite's native inline "New" creation for a List/Record sublist field exposes the originating transaction and line to a script on the child record at all — this determines whether the simpler approach sized here is technically achievable as scoped, or whether a larger UI-based approach is required.

Key assumption: the sublist field on the Purchase Order line is a List/Record type field referencing customrecord_rax_lot, with an internal ID that has not yet been confirmed against the account. Key risk: context-passing feasibility, above.

Solution Approach

Name field: No development work. Since auto-generated numbering is already enabled on the customrecord_rax_lot record type, the Name field can be removed from user entry by disabling "Include Name Field" (or confirming numbering fully suppresses manual entry) on the record type definition. Before making this change, existing saved searches, scripts, or reports that reference the record's Name/altname field should be checked so nothing downstream breaks.

Item autofill: A script deployed on the Lot record type will trigger when a Lot record is created inline from a Purchase Order line, resolve the originating PO and line, and set the Item field to match that line's item — including overwriting any value already present, consistent with the confirmed business rule. If the PO line has no item selected, the Item field is left blank without blocking the save. This depends on confirming that NetSuite passes enough context (the parent transaction and line) to the Lot record at creation time; this will be verified early in the build (see Risks) before development proceeds on the assumed approach.

Testing Steps

  • Positive: Add a PO line, select "New" on the Lot sublist field, save the new Lot record — Item matches the PO line's item.
  • Overwrite on edit: Edit an existing Lot record whose Item differs from its originating PO line — Item is corrected to match the PO line on save.
  • Negative / blank item: PO line has no item selected when the Lot record is created — Item remains blank, no error, PO save is not blocked.
  • Multiple lines: A single PO with several lines, each with its own new Lot record — each Lot record's Item matches only its own line, not another line's item.
  • Regression: Confirm the existing rax_ue_lot_capture.js behavior on Assembly Build, Item Fulfillment, and Item Receipt is unaffected.
  • Role/permission context: Confirm the autofill behaves consistently for the roles that create Purchase Orders and Lot records (e.g., Purchasing, Warehouse).

Considerations

  • The sublist field's internal ID (assumed custcol_rax_lot) has not been confirmed against the account and must be verified before build.
  • If NetSuite's native inline-creation popup does not expose the parent transaction/line to the Lot record, the fallback is a custom button/Suitelet that passes context via URL parameters — a materially larger Suitelet & UI-sized effort. This estimate assumes the simpler path is viable and should be confirmed with a short technical spike before committing to final hours.
  • Per N/query / search.lookupFields best practice, the PO line item lookup will avoid loading the full PO record where possible.

Assumptions & Out of Scope

  • Assumes auto-generated numbering is already fully configured and functional on customrecord_rax_lot (no numbering setup work included).
  • Out of scope: any change to rax_ue_lot_capture.js or its deployments.
  • Out of scope: cleanup or deletion of a Lot record when its originating PO line is later removed — orphaned records are left as-is.
  • Out of scope: any handling of the Direction custom-list mapping noted as unresolved ("left for setup") in the existing script.
  • Out of scope: CSV import or SuiteQL/search-based paths for Lot record creation — only the PO-line inline-creation path is covered.

Risks

  • Feasibility (High): Native List/Record sublist "New" creation may not pass the parent transaction/line context to the child record. Verify via spike before development; if unsupported, re-scope to a Suitelet/UI-based approach.
  • Field ID accuracy (Low): The sublist field ID and its relationship to customrecord_rax_lot should be confirmed directly in the account rather than assumed.
  • Orphaned records (Low): Lot records tied to removed PO lines are not cleaned up, which may accumulate stale traceability records over time; acceptable per current scope decision.
